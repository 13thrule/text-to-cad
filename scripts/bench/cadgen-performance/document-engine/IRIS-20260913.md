# Mechanical iris: larger-model checkpoint, 13 September 2026

The 118-occurrence mechanical iris meets the requested roughly 20-second old-engine build size. The complete-request comparison at `408e7c8b9` fails the performance gate: every measured scenario is slower than the frozen old engine. All 24 measured STEP outputs pass independent geometry checks. Passing the harness means geometry parity, not a performance win.

## Scope and method

The old revision is `5c4a212cae32e834fa4d805ae778ab5ee6cd71a2`, the pushed rollback checkpoint. It already contains the earlier branch optimizations; it is not original main. The replacement revision is `408e7c8b92c5d5a4aba65183625887bbacd9415c`, still an internal engine rather than the public default. Both Python runtime trees were archived before the run and remained unchanged.

The source is `models/assemblies/src/mechanical_iris_aperture/mechanical_iris_aperture.py`. The harness preserves its modeling helpers, redirects the declared STEP into its private fixture directory, and records source execution. Outputs are approximately 12.72 MB, with 118 occurrences and 91 STEP prototype copies in each changed candidate export. The geometry edit changes the base-ring mounting-hole diameter; the placement edit moves only that base ring along Z.

There are three cold samples and three samples per warm scenario, after one unmeasured prime per warm session. Engine order alternates by cold pair or whole warm-session pair. Each complete request includes input delivery, native/source work, required STEP completion and actual destination-byte verification. Cold additionally includes worker launch and engine setup. Independent saved-file geometry oracles and display derivation are outside both engines' request timings. The boundary identifier is `captured-entry-to-attested-step-pair-full-request-v2`.

All task agents paused native work during the series. An unrelated existing viewer used 5–43% of one CPU before measurement and remained running. This is a desktop observation with three samples, not an idle-host confidence interval or p95 claim. Old placement timing has substantial variation; its full range is retained below.

## Attribution and next work

Both unchanged and placement calls reuse all 28,196 recorded operations with zero newly computed operations. They still execute Python once and perform 370 native copies. The unchanged STEP product itself is reused: zero STEP prototype copies, independent parses or writes. The old unchanged gate skips the source body, whereas the replacement replays ordinary Python. That semantic difference is explicit, but does not excuse the user-visible regression.

Each mounting-hole edit computes 3,088 operations and reuses 25,108. These counts include topology projections and other graph operations; they are not counts of expensive booleans. Candidate source/geometry medians are 6.125 s unchanged, 6.508 s for the hole edit and 6.144 s for placement. Changed STEP product completion adds approximately 3.3–3.6 s, including 91 prototype copies and one independent parse.

A separate frozen, in-process diagnostic shows no native escape in either cold or warm execution. Two unprofiled unchanged replays took 5.978 and 5.989 s. The warm cProfile run attributes most time to live provider checks: broad builder checks total 8.09 profiled seconds, scalar-query checks 5.04 seconds, and `inspect.getattr_static` runs 2.43 million times. These overlapping profile entries are attribution evidence, not additional request timings or speed ratios. Core evaluation bookkeeping is much smaller.

Revision `97b66f1a2` compiles callback-safe lookup inventories and avoids repeatedly fingerprinting deeply immutable function defaults while still checking every live mutable binding. It has not been included in the frozen matrix above. A new frozen series must measure its actual impact before a performance win is claimed. Unchanged replay, required STEP completion, public integration and the remaining plan gates stay open.

### Subsequent internal diagnostics

Two frozen `97b66f1a2` in-process diagnostics took 3.354 and 3.544 s for an unchanged iris call, down from the earlier diagnostic's approximately 5.98 s. These exclude controller IPC and use a different boundary from the full-request table. They show progress within the replacement, not a matched old/new speedup. One instrumented-stage run took 22.986 s cold and 7.089 s for the mounting-hole edit. The unchanged call still replays Python and reuses all 28,196 operations; the hole edit still computes 3,088 and reuses 25,108.

Direct `perf_counter` wrappers around the STEP stages separate the hole edit's 3.194 s product preparation:

| Private XCAF composition, including 91 prototype copies | 0.049 s |

Of readback, about 1.392 s is parsing/transfer and 1.065 s is metadata and geometry diagnostics. The latter includes 0.500 s for all exact bounds and 0.552 s for local geometry facts excluding bounds. These nested values must not be added again to the table. A separate parse of the same saved bytes attributes material cost to the non-gating validity calculation; prototype copying is not the principal export bottleneck. Its baseline and instrumented parse differed noticeably, so neither diagnostic supplies a performance ratio.

The cProfile data omits some expected frames on this interpreter. It is useful for identifying repeated calls but not an exhaustive accounting of request time; the direct stage timers above avoid relying on those missing frames. No new saved-file oracle series or browser timing is claimed for these diagnostics. The public engine has not been cut over.

## Display diagnostic

The candidate separately derives a pinned native display after each generation session. This is mesh preparation and transfer through the document worker, not browser frame presentation, and there is no old/new rendering ratio. The first cold session produced 91 assets totaling 1,466,776 bytes, plus a 71,763-byte manifest, in 862.686 ms. The entire iris has not passed the six-fixture mesher's strict surface-quality oracle, so this number is not a quality-matched rendering speedup.
