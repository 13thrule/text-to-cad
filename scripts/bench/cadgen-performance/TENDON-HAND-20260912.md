### Bottlenecks found during this review

The warm build spent 59.66 s publishing the canonical saved document. Bounding
box memo lookup copied and hashed placed native shapes despite already owning
verified component BREP identities. The replacement uses the existing runtime-
scoped operation index, keyed by BREP, codec, native leaf and exact rotation.
It still measures tight native extrema on a miss and applies translation to
each leaf before merging. Tests require the complete tree and hash to match the
ordinary bounds path exactly; incomplete private input falls back to that path.

The warm browser Render transition made 55 singleton detail publications and
spent 50.14 s in scene adoption. Every publication repeated the full assembly's
animation/effects traversal. Refinement now collects up to four admitted
components over a bounded 128 ms window. Exact payload reservations and top-ups
still enforce admission; pressure-driven coarsening stays singleton. This does
not change mesh quality, memory limits, animation semantics or first geometry.

### Existing component identity churn

The legacy baseline itself republished different component identities for
unchanged STEP bytes. Subsequent candidate runs continued that behavior. The
respective runs changed 176, 163 and 149 component payloads, creating roughly
29, 26 and 24 MB of new BREP bytes. The changes were all binary-v4 to binary-v4;
names, assembly structure, placements, face colors, stats and aggregate bounds
were exact. Codec checks protect native point records, but this review does not
claim exact stability of every underlying curve/surface coefficient.

That existing decode/re-encode churn reduces mesh and operation-cache reuse.
It is not fixed by the bbox helper. A separate same-loaded-scene comparison
proved the complete legacy/candidate tree and hash equal (`823cf719…`), avoiding
the cross-process drift as a confound for bounds correctness. The review store's
document index and model record were restored to the original verified saved
tree before the paired browser comparison.

The larger follow-up is to retain the verified canonical-document snapshot
privately through warm STEP readback and reuse its identities after exact-byte
verification. It must retain correspondence checks, private native ownership,
and recovery when backing objects disappear. It must not trust a mutable scene
or alias a source result to saved STEP bytes.

The repeated CLI snapshot remains a separate performance gap. Static inspection
shows each invocation creates a fresh browser, reconstructs a disposable package
view, decodes roughly 447 MB of cached L1 arrays, and composes 3,259 display
records. The uniform L1 scene has roughly 91 million triangles across occurrences.
Snapshot tight framing also visits the vertex positions of each visible
occurrence before the first draw and PNG readback. These are candidate costs,
not measured stage attribution for the 181–200 s totals.

The next diagnostic is to preserve the browser's existing `stageTimings`
(`headlessRenderEntry.js`) and capture timings through `snapshot_core.py`;
currently Python retains only resolve-time debug information. This would
separate package loading, scene construction and capture before selecting a
snapshot optimization. Snapshot implementation is unchanged in this review.

### Validation limits

The all-placement native self-intersection check was stopped after about 191 s,
having checked six of 866 prototypes without findings. This is **partial
validation**, not a geometry certification. The website's five GLBs and its
optional video were not regenerated.

The ignored 11 MB animation module was restored from the preserved generated
output. Its frame manifest and runtime match this rebuild byte-for-byte; all
1,886 referenced bodies resolve. Node execution of seven clips at start, middle
and end passed, including 18,333 body lookups and 1,008 tendon deformation calls.
No nine-minute route re-solve was needed.

In the actual in-app browser, component selection and lazy topology loading
worked: the wrist cradle's B-spline face resolved to `o1.5.f3`, showing area
58.68 mm² and a copyable reference. Starting the Make-a-fist clip advanced the
clock, but pausing timed out twice while the page was busy. Reloading retained
the paused nonzero time and also became sluggish during loading. The owned test
tab was closed to release its resources. This is an observed playback
shortcoming; the successful synthetic module checks above do not establish
usable full-hand animation in the browser.

A bounded follow-up Chromium profile with no loaded selectors confirmed real
geometry motion into the fist pose. Inspect scrubs from 0 to 3.00 s and from
3.00 to 3.10 s took approximately 563 and 569 ms, respectively, excluding the
explicit three-second observation wait. The latter is an authored hold, yet
still pays roughly the same cost. Analytic tendon-path compilation and frame
transport account for approximately 350–400 ms of sampled JavaScript work;
Inspect also deforms the 48 visible tendon edge objects on the CPU. Surface
deformation already uses the GPU where eligible. Per-frame transformed selector
reconstruction is a plausible additional cost when topology is loaded, but that
case was not CPU-profiled, so its contribution remains unmeasured.

In a fresh in-app Render view, the paused 3.00 s fist pose also rendered correctly.
Playback advanced; a pause action timed out at the automation interface, and a
later UI read confirmed playback had paused. Thus animation is functional in
both modes, but smooth full-hand playback is not established. The hand viewer
was left open in Render for user review. Animation runtime code is unchanged
in this review.

There is no matched FreeCAD run for this hand. Historical branch figures used
different detail policies and animation conditions and cannot support a causal
speedup or parity claim.
